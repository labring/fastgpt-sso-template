# 三主体企业微信 SSO 设计

## 目标及已确认需求

仅对接企业微信，三个独立企业微信主体接入同一套 FastGPT。用户登录前选择所属企业。同步三个主体在应用可见范围内的成员、部门和组织关系，保持现有 FastGPT 接口结构及同步 Bearer 鉴权。

## 方案比较

采用一个服务、一个 wecom provider、三套主体配置及统一选择页。用户已确认同一 FastGPT 和先选择企业的方式。三个服务分别部署需要额外聚合同步及登录入口；修改 FastGPT 维护三个登录入口会增加上游改造成本。本次采用单服务聚合。

## 登录流程

1. 保留 GET /login/oauth/getAuthURL，验证 redirect_uri 是否匹配配置的 FastGPT 回调地址白名单，生成短时登录事务，返回本服务企业选择页地址。
2. 选择页只展示配置的企业名称。选择企业后生成密码学随机 state，服务端记录所属企业、原始 FastGPT state、回调地址、过期时间。绑定浏览器 HttpOnly cookie，拒绝篡改、过期及跨事务回调。页面使用服务端 HTML，不引入前端框架。现有 provider 契约不能直接设置响应 cookie，新增选择页及选择企业 HTTP handler 负责设置 cookie，provider 负责生成授权及回调地址。
3. 跳转所选企业的企微 Web 登录入口；授权回调统一进入本服务 /login/oauth/callback。企微 state 与 FastGPT state 分开管理，不能用共享变量存储回调地址。
4. 使用事务内企业配置兑换企微身份，校验是该企业有效成员并读取必要资料。拒绝外部身份或不可读取的成员。签发随机、短时、一次性本地 code，将 code 及原 FastGPT state 通过 URL API 加入 FastGPT 回调地址。
5. GET /login/oauth/getUserInfo?code=... 消费本地 code，返回现有 username、memberName、avatar、contact 字段。无授权的资料使用空值，不用手机号作为身份标识。

具体企微端点、参数、权限及移动端行为在实现前以可访问的官方资料和真实联调核实；本次以浏览器 Web 登录为交付入口。

## 身份和组织映射

- 每个主体配置稳定、唯一的 key（例如 corp-a），显示名可修改，key 投产后不得随意修改。
- username 使用 wecom:<key>:<编码后的userid>，登录和同步共用同一映射函数。编码必须可区分原始特殊字符，不能简单替换导致碰撞。
- 部门 ID 使用 wecom:<key>:dept:<部门ID>；每个企业增加 wecom:<key>:root 根节点，parentId 为空字符串（按当前 FastGPT 官方文档修正旧模板的 '0' 示例）。企微顶级部门挂在企业根节点下。实施前核对 FastGPT 对 username、组织 ID 的字符及长度限制，必要时调整编码格式，但保持稳定与无碰撞。
- 用户 orgs 使用映射后的部门 ID。每个主体内部按 userid 去重，保留多部门归属；不同主体的同一个人视为两个账号，不按姓名或手机号合并。
- 可见范围不包含父部门时，将可见部门挂在主体根节点下；不得产生悬空 parentId 或 orgs。
- 本次假设该 FastGPT 为首次导入这些身份；已有账号迁移和身份合并不在本次范围。

## 通讯录同步

保留 GET /user/list 与 GET /org/list 及 AUTH_TOKEN 鉴权。同步使用三个主体各自自建应用的配置，默认与登录共用应用；如需不同 secret，可为每个主体配置单独的通讯录读取 secret。实际同步范围取决于该凭据权限，部署文档明确配置可见范围及可信 IP 的要求。

统一生成包含所有主体的成员与组织快照，两个接口读取同一短时缓存，避免重复拉取。快照必须完整校验后原子替换；同一时刻的请求复用进行中的拉取任务。短时缓存不保证分开的两次 API 请求跨缓存更新时间具有事务一致性，此限制写入文档。

任一主体拉取失败或响应结构异常，整次刷新失败，不返回部分成功或用空数组替代失败主体；过期后刷新失败明确返回错误，不静默用旧数据冒充成功。上游请求设置超时，限制并发，按接口能力处理分页、去重及 token 过期刷新，错误信息不包含凭据、token 或完整上游响应。同步仅提供被 FastGPT 拉取的接口，不增加定时任务或通讯录事件订阅。

## 配置和运行边界

通过环境配置三个主体的 key、name、corpId、agentId、appSecret 及可选通讯录 secret；文档和 .env.template 只包含占位值。配置本服务公开 URL、FastGPT 回调白名单及 AUTH_TOKEN。校验配置缺失、主体 key 重复及 URL 不合法，生产环境缺失关键配置应启动失败。

默认单实例，登录事务、一次性 code、access_token 与同步快照保存在进程内并及时清理。重启会使未完成登录失效，需要重新登录。多副本共享存储不在本次范围；部署说明明确禁止直接无状态扩容。

删除通用 OAuth2、演示登录、SAML 入口和无关依赖，注册 wecom 为唯一 provider；未知 provider 配置显式拒绝。保留 SSO_PROVIDER / SSO_SYNC_PROVIDER 配置兼容性，两者只能选择 wecom，同步未配置时回退至登录 provider。统一 Bun 构建和运行路径，配置变更同步 README。

## 验证与交付

- 运行 package.json build 脚本；补充有意义的类型检查和针对身份映射、事务消费、组织映射的测试。
- 启动真实 HTTP 服务，使用本地模拟企微端验证选择企业、三主体登录、state/cookie 校验、code 一次性和过期、回调白名单、重复 query 参数拒绝。
- 验证三主体用户、组织聚合及跨主体同 ID 隔离，多部门归属、父节点缺失、上游失败、token 失效等边界。
- 缺失及错误 Bearer token 返回 401，正确 token 返回契约数据；验证 provider 默认、显式配置、未知配置行为。
- 无真实企业凭据时不声称真实企微联调通过；交付可按文档填写的配置及真实联调检查步骤。

## 待用户审阅的实现选择

身份跨主体隔离且不自动合并；每个企业独立根节点；先支持单实例；失败时拒绝部分同步。这些为实现建议，尚未视为用户已确认的细节。

## 2026-11-09 追加需求

用户确认支持 1～3 个主体以便逐步接入，替代原先必须恰好三个主体的配置限制。保留已有主体 key 和身份映射，选择页及同步仅处理已配置主体。空数组、超过三个及重复 key/corpId 仍拒绝启动。

## 2026-11-10 同步兼容性修正

FastGPT 标准组织接口只允许一个根部门。增加唯一总根 wecom:root（企业通讯录），各企业 wecom:<key>:root 挂在其下，原用户及部门 ID 保持不变。此修正替代早期设计中多个无父级企业根节点的方案。FastGPT 既有用户名重复键属于导入端数据/匹配问题，不能通过重命名或删除用户绕过。

## 2026-11-10 原版 Pro 用户名前缀兼容

用户明确要求不修改 Pro，并确认自行删除旧测试账号，不考虑旧账号迁移。因此将 username 改为 wecom-<key>:<小写编码userid>，确保原版 Pro 取第一个连字符前的片段时均得到 wecom。登录和同步共用映射，组织 ID 不变；不运行任何删除或数据库迁移。此规则替代初版的冒号前缀用户名。
